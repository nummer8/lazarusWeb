# Plugin Usage Guide (Step by Step)

> Goal: **leave the main framework untouched; adding a feature just means adding files**.
> This document only covers how to use it; for why it is done this way (cross-DLL class identity experiments, four-approach comparison) see
> `PLUGIN_FEASIBILITY_en.md`.

---

## 0. Understand it in 30 seconds

A "plugin" is just an ordinary unit that satisfies two conventions:

```pascal
unit umod_xxx;                       { 1) one .pas file }

interface
procedure RegisterModule;            { 2) declare this name in the interface section }

implementation
procedure RegisterModule;
begin
  TLWApp.RegisterForm('Xxx', TXxxForm);   { page: registered name -> form class }
  TLWApp.AddAjax('xxx_data', @GXxx.Data); { optional: AJAX endpoint }
end;
end.
```

The main program calls `RegisterAllModules` only once (this unit is generated by the script that scans the directory), so **adding a plugin does not require changing the main program**.

Both UI styles are supported; choose according to your habit:

| Style | Suitable for | Example |
|---|---|---|
| `.lfm` designed form + `{$R *.lfm}` | Conventional Lazarus practice, drag controls in the IDE | `plugins/umod_notes.pas` |
| Build the form in pure code | UI generated dynamically from data, or no design file desired | `plugins/umod_dashboard.pas` |

## 1. First, Run the Existing Demo

```bat
cd C:\lazarusWeb

rem Generate the registration summary (run it after adding/renaming a plugin; also registers plugin units in the lpi so they can be designed in the IDE)
python tools\lwplugins.py --lpi demos\plugindemo\plugindemo.lpi --lpi demos\plugindemo\plugindemo_gui.lpi

rem Build the nogui tier (console service)
lazbuild --ws=nogui demos\plugindemo\plugindemo.lpi

rem Start (port read from demos\plugindemo\plugindemo.ini, default 8877)
demos\plugindemo\plugindemo.exe
```

Open <http://127.0.0.1:8877/> in a browser; you should see the "Module Dashboard": three metric cards, a progress bar, two buttons, and a log box.

**To see the second page**: click **"Open Notes Page"** on the page — the browser switches to the notes page (the dashboard window is removed, but the server-side instance is kept), then click **"Back to Dashboard"** inside it to switch back. This is the page-switching semantics of `TLWApp.OpenForm('registered name')`.

You can also specify the default page at startup:

```bat
demos\plugindemo\plugindemo.exe --form=Notes
```

Expected result: page title "Notes (Plugin)", with a title input box, a content box, Save/Clear/Back buttons, and a saved list.

GUI tier (pops up a server panel, or use `--nogui` to skip it):

```bat
lazbuild demos\plugindemo\plugindemo_gui.lpi
demos\plugindemo\plugindemo_gui.exe --nogui
```

The port is in `demos\plugindemo\plugindemo_gui.ini` (8890).

## 2. Add a New Page (5 Steps)

Take adding an "Order Page" as an example.

**Step 1: Copy the template**

```
plugins\template\umod_template.pas   ->  plugins\umod_order.pas
plugins\template\umod_template.lfm   ->  plugins\umod_order.lfm
```

**Step 2: Change three places**

| What to change | From | To |
|---|---|---|
| `unit` name (matches the file name) | `umod_template` | `umod_order` |
| Class name (change the `.lfm` root object type accordingly) | `TTplForm` | `TOrderForm` |
| Registered name | `'Tpl'` | `'Order'` |

The first line of the `.lfm` must change too:

```
object Order: TOrderForm
```

**Step 3: Generate the registration summary**

```bat
python tools\lwplugins.py --lpi demos\plugindemo\plugindemo.lpi --lpi demos\plugindemo\plugindemo_gui.lpi
```

The output should contain:

```
  模块  umod_dashboard.RegisterModule
  模块  umod_notes.RegisterModule
  模块  umod_order.RegisterModule
  lpi  ...plugindemo.lpi：已登记 4 个单元
```

**Step 4: Rebuild (with `-B`)**

```bat
lazbuild --ws=nogui -B demos\plugindemo\plugindemo.lpi
```

> When you change the `.lfm` you must include `-B`: `lazbuild` does not record `.lfm` files in the dependency table; without it the old UI is silently used.

**Step 5: Open**

```bat
demos\plugindemo\plugindemo.exe --form=Order
```

Or call `TLWApp.OpenForm('Order')` from another page's button.

## 3. Integrate into Your Own Project

Prerequisite: the project is a lazarusWeb project (form base class `TLWForm`, able to run `TLWApp.Run`).

**3.1 Create the plugin directory** (under the project directory, e.g. `C:\MyApp\plugins\`), copy the template `umod_template.pas/.lfm` into it, rename it, then write the first module.

**3.2 Add two lines to the main program**

```pascal
uses
  Interfaces, Forms, lwapp, umain, lwmodules;   { add lwmodules }

begin
  Application.Initialize;
  Application.Title := 'MyApp';
  TLWApp.Register(TMainForm);    { keep the original form, no impact }
  RegisterAllModules;            { add this line: register all plugins }
  TLWApp.Run;
end.
```

**3.3 Add the unit search path to the project**

Lazarus IDE: `Project → Project Options → Compiler Options → Other unit files`, and add your plugin directory:

```
..\plugins
```

Framework units do not need to be added again:

- IDE-wizard-generated projects **depend on the `lwserver` package** (`lwform`/`lwapp`/`lwajax`/`lwpluginutil` are all in the package), so you only need to add the plugin directory;
- Projects generated with the `tools\lwnew` command line use source paths; `src\core` is already in `Other unit files`, so again you only need to add the plugin directory.

> Check both build modes (Default / GUI): if a mode also has its own copy of `Other unit files`, it overrides the Default one and needs to be added there as well.

**3.4 Generate the registration summary**

```bat
python C:\lazarusWeb\tools\lwplugins.py --dir C:\MyApp\plugins --lpi C:\MyApp\MyApp.lpi
```

`--dir` is your plugin directory; `lwmodules.pas` will be written to `<dir>\lwmodules.pas`; `--lpi` makes the plugin units visible in the IDE's project inspector (you can pass multiple lpi files repeatedly).

**3.5 Build and run**

```bat
lazbuild --ws=nogui -B C:\MyApp\MyApp.lpi
```

Afterwards, adding a plugin only repeats 3.1/3.4/3.5; the main program and the `.lpi` need no further changes.

## 4. UI: Three Notes About `.lfm`

```pascal
type
  TOrderForm = class(TLWForm)
    edNo: TEdit;                       { 1) field name = .lfm component name }
    btnSave: TButton;
    procedure btnSaveClick(Sender: TObject);   { 2) the event method is in this section too }
  end;

implementation
{$R *.lfm}                             { 3) compile the .lfm into the exe resource section }
```

1. **Fields have the same names as components**. Renaming a control in the IDE automatically syncs the field; when editing the `.lfm` by hand you must align them yourself; a mismatch → the field is `nil` and accessing it at runtime causes an AV.
2. **Fields and event methods must be in the default visibility section of the class declaration** (after `class(TLWForm)` and before `private`, equivalent to published). LCL's `TReader` relies on RTTI to connect components and `OnClick = btnSaveClick`; putting them in `private` prevents the connection, and clicks have no effect.
3. **No need to register the resource in `.lpi`**. The `.lfm` is compiled into the exe resource section by `{$R *.lfm}` and looked up by `TForm.Create` by class name; `.lpi` only registers `.pas`.

**Designing the UI in the IDE**: open `demos\plugindemo\plugindemo.lpi`, double-click `umod_notes.pas` in the project inspector, and press **F12** to enter the designer. After saving the change → run the generator (optional) → rebuild with `-B`.

**Multiple sessions**: when the same page is opened in multiple browsers, LCL appends `_1/_2` to the instance name; `TLWForm.Loaded` already restores it to the design-time name, so no handling is needed.

## 5. Jumping Between Pages

```pascal
if not TLWApp.OpenForm('Notes') then
  ShowMessage('没有注册名为 Notes 的窗体');
```

- Repeated calls within the same session **will not** create a second instance (it first checks for an existing form in the session);
- The semantics are **page switching**: other visible pages in the browser are removed (`SessionHideOthers`), leaving only the target page. The server-side form objects all remain in the session; switching back returns to the same instance, so control states and entered content are not lost;
- When the target page is already the only visible page (clicking the navigation again on the current page), it is not pushed again, avoiding duplicate window creation on the frontend;
- If you truly want multiple windows to coexist, do not use `OpenForm`; call `Form.Show` directly (which goes through `SessionShowForm`).
- Modal forms do not participate in switching: opening another page during `ShowModal` does not remove the modal form.

## 6. AJAX Endpoints

Server side:

```pascal
type
  TOrderAjax = class
  public
    procedure List(A: TLWAjaxContext);
  end;

procedure TOrderAjax.List(A: TLWAjaxContext);
begin
  A.Json('{"ok":true,"items":["A-1","A-2"]}');
end;

// In RegisterModule:
TLWApp.AddAjax('order_list', @GOrderAjax.List);
```

Browser:

```js
const r = await fetch('/lw/ajax/order_list');
const data = await r.json();
```

To allow direct calls from third-party sites (cross-origin), add `--ajax-cors` at startup.

When you need to build a JSON string by hand, use the escaping function in the framework unit (`src/core/lwpluginutil.pas`):

```pascal
uses lwpluginutil;
A.Json('{"ok":true,"name":"' + JsonEscape(edName.Text) + '"}');
```

## 8. Deployment

At runtime, front-end resources are searched in the order `<root>\lw\<file>` → `<exe directory>\lw\<file>` → upward search for `src\client`. **When copying outside the repository for standalone deployment**, copy the entire `src\client` into an `lw\` directory alongside the exe, and put `favicon.ico` alongside the exe:

```
MyApp\
  MyApp.exe
  MyApp.ini
  favicon.ico
  lw\  (lw.js / lw.css / alpine.min.js / ...)
```

For multi-process / zero-downtime releases use `lwhyper` (rolling repackaging, restarting workers one by one), which is outside the scope of this document.

## 8.5 Another Form of Plugin: Independent exe (Process-level Plugin)

Rather than being linked into the host, plugin units are installed into an **independent lazarusWeb service exe** (listening on its own port), and the host uses `lwroute` to reverse-proxy `/p/<name>/...` to it. For the full demo and principles see `demos/procdemo/README.md`; for the trade-off comparison with the compile-time form see `PLUGIN_FEASIBILITY_en.md` §4/§5.

```ini
; Register in the host ini (key name is fixed as plugin.<name>=host:port)
plugin.notes=127.0.0.1:8871
plugin.dash=127.0.0.1:8872
plugin.reports=127.0.0.1:8873
```

The demo project `demos/procdemo/` ships its own plugin module sources (`modules/`), which are not shared with the compile-time form's `plugins/`; the two sides are independent copies, and changing one does not affect the other.

The plugin exe is just an ordinary lazarusWeb application, and the module unit is **not changed at all** compared with the compile-time form:

```pascal
program notesplug;
uses Interfaces, Forms, lwapp, umod_notes;
begin
  Application.Initialize;
  RegisterModule;          { the same module contract as plugindemo }
  TLWApp.Run;
end.
```

Opening a plugin page from a host page:

```pascal
procedure THostForm.OpenNotes(Sender: TObject);
begin
  RunJS('location.href=''/p/notes/''');   { TLWForm.RunJS: jump in the current tab }
end;
```

After the same-tab jump, press the browser's "Back" to return to the host; use `window.open('/p/notes/', '_blank')` only if you want a new tab. The plugin-side code is identical in both cases — the plugin does not know who opened it, and the API derives BASE from the page path and automatically falls back to the proxy prefix.

**Navigation between plugin pages** (calling `TLWApp.OpenForm('registered name')` in the module): the module source code is unchanged between the two forms, and the framework decides which path to take based on the registration —

| Form | Behavior of `OpenForm('Notes')` | Configuration needed |
|---|---|---|
| Compile-time (plugindemo) | Two forms in the same process, directly create/switch the form | None |
| Independent exe (procdemo) | The process only has its own forms; target not found → push JS to jump to the mapped URL | Each plugin's ini configures `page.<registered name>=<URL>` |

In the independent exe form, the dash process has no Notes form (it lives in the notesplug process), so configure a line in dashplug.ini pointing the registered name to the other side's page URL; to be able to return to the host home page, also point `page.Host` to the host root path `/`:

```ini
; dashplug.ini -- clicking "Open Notes Page" calls OpenForm('Notes') and jumps here
page.Notes=/p/notes/
page.Reports=/p/reports/
page.Host=/

; notesplug.ini -- clicking "Back to Dashboard" calls OpenForm('Dashboard') and jumps here
page.Dashboard=/p/dash/
page.Reports=/p/reports/
page.Host=/

; reportsplug.ini -- the buttons call OpenForm('Dashboard') / OpenForm('Notes') respectively
page.Dashboard=/p/dash/
page.Notes=/p/notes/
page.Host=/
```

**Every plugin page must be configured with all of "the other two plugins + Host"**; if one is missing, the corresponding button's `OpenForm` returns False (the button click has no effect), and this is not a routing problem. `page.Host=/` uses the host root path; when you open the page by connecting directly to the plugin port, clicking it returns to the plugin's own home page.

The URL uses the absolute path `/p/<name>/`; after the browser executes `location.href`, the host `lwroute` proxies it to the target plugin process. The framework implementation is in `lwapp.OpenForm`: it first looks for a local form, then checks the `page.*` mapping if not found, and on a hit pushes `{"type":"js","code":"location.href='…'"}`; only when neither is found does it return False (consistent with the old behavior). Note: **having the mapping configured does not mean they can coexist on the same screen** — in the independent exe form, `OpenForm` is a full-page jump (same tab), not multiple coexisting windows.

Boundaries: independent sessions (plugins have their own sid/login); WebSocket is not yet passed through the proxy (the frontend automatically falls back to long polling); adding controls to an existing host page is not possible (that is the job of the compile-time form).

Division of responsibilities (default behavior): **plugins only handle business, non-business functions are handled by the main program** — framework static resources (`lw.js` / `lw.css` / `lw-alpine.js` / `lw-alpine.css` / `alpine.min.js`, `favicon.ico`, `/ext/`) are served directly by the host when passing through the proxy, and are not forwarded to the plugin (`lwroute.LWRouteStaticLocal` whitelist). Therefore:

- Upgrading the client runtime only requires changing one place, the host, and all plugin pages take effect immediately;
- Plugin deployment can carry only the exe (when connecting directly to its own port for debugging, `LWFindClientFile` serves as normal, unaffected);
- Session-bound endpoints (`/lw/api/*`, `/lw/ajax/*`, captcha, `/lw/tpl/` templates) keep their state in the plugin session and are still proxied back to the plugin; the host does not intercept them.

### Form templates for plugin pages

Plugin forms use exactly the same template mechanism as ordinary forms; no Pascal code is needed:

- File names: desktop `<form runtime root>\tpl\<form name>.html` (window and flat modes share this one file), mobile `<form name>.m.html` (mobile is read-only; without a template, the LCL layout is used); the file header must be written as `<!-- lw-tpl-mode:window -->` or `<!-- lw-tpl-mode:flat -->`; when both appear, **flat takes priority**. The template serves only as a background/decoration layer; controls are always absolutely positioned by the `.lfm`'s `Left/Top`, and the old `{%control name%}` streaming placeholders are no longer supported;
- One-click generation: in the IDE, open the plugin form's `.pas`/`.lfm`, use **Tools → Generate lazarusWeb Form Template (Current Unit LFM)**, select window or flat mode in the popup, and generate into the project directory `tpl\` (desktop `.html` + mobile `.m.html`, two files). If you have modified the `lwdesign` package source, you must first Compile → Install in the IDE and restart, otherwise the menu still uses the old logic;
- Deployment: put the generated `.html` and `.m.html` into the **plugin exe's runtime root** `tpl\`. When accessed through the host `/p/<plugin name>/` proxy, `/lw/tpl/<form name>.html` carries the plugin session `sid` and is proxied back to the plugin, so template state lives on the plugin side; static client resources (`lw.js`/`lw.css` and `lw-alpine.js`/`lw-alpine.css`, `alpine.min.js`) are served directly by the host whitelist, so each plugin does not need its own copy. When connecting directly to its own port for debugging, the plugin exe directory must also have the updated `lw\` resources;
- If an old `<form name>.flat.html` remains in the directory, the compatibility rule still triggers flat mode; to switch back to window mode, delete it; after changing the template, force-refresh with `Ctrl+F5` (client scripts are cached).

## 9. Regression Tests

```bat
rem Terminal 1
demos\plugindemo\plugindemo.exe --port=8877 --form=Dashboard

rem Terminal 2
python tests\t_plugin.py
```

Coverage: session establishment, plugin form instantiation (node tree), button click dispatch, cross-plugin navigation, two AJAX endpoints, default form name.

> The event name in the script must be `OnClick` (the published event name). Passing `"click"` is silently ignored by the framework — it looks like "the click has no effect". In addition, memoLog initially has a "Refresh: ..." line, so the assertion must compare the text difference before and after the click; checking only for keywords yields false positives.

## 10. FAQ

| Symptom | Cause | Solution |
|---|---|---|
| No new page in the browser | Didn't run the generator / didn't rebuild / wrong `--form=` name | Run the generator → rebuild with `-B` → use the registered name from `RegisterModule` |
| Blank page, all styles lost | Deployment directory missing `lw\` (when connecting directly for debugging) | Copy `src\client` into an `lw\` directory alongside the exe; when proxied through the host, the host serves it directly, so the plugin does not need to carry it |
| Plugin template not taking effect | File not at the plugin runtime root `tpl\<form name>.html`, or missing the `lw-tpl-mode` marker; or a leftover old `.flat.html` forcing flat mode; or client script cache | Put it in the plugin exe root `tpl\`, write `lw-tpl-mode:window\|flat` in the file header, delete the old `.flat.html`, force-refresh with `Ctrl+F5` |
| Changed `.lfm` but the UI didn't change | Didn't include `-B` | `lazbuild -B ...` |
| Button click has no effect | Fields/event methods placed in `private`; or component name differs from field name | Move to the default visibility section, align the names |
| Runtime AV, field is nil | No such component in the `.lfm`, or name mismatch | Check the `.lfm` against the class declaration |
| IDE project inspector doesn't show plugin units | Didn't pass `--lpi` | `python tools\lwplugins.py --lpi <your.lpi>` |
| Double-clicking `.lfm` doesn't open the designer | The unit isn't in any project's search path | Open the project → add the plugin directory to Other unit files → press F12 from the `.pas` |
| `Identifier not found "TPanel"` | Missing `ExtCtrls` | `uses ... ExtCtrls` |
| `Can't create object file ... .exe` | The exe is running, file is locked | Close the service before building |
| Two plugins registered the same name | The later registration overrides the earlier one | Keep registered names unique (checkable with `FormNames`) |
| Chinese garbled text | Source file isn't UTF-8 | Save both `.pas`/`.lfm` as UTF-8 (Lazarus default) |

## 11. Checklist After Adding a Plugin

- [ ] File name, `unit` name, class name, `.lfm` root object type, and registered name are all consistent
- [ ] `interface` section has `procedure RegisterModule;`
- [ ] `.lfm` exists and the unit has `{$R *.lfm}`
- [ ] Fields and event methods are in the default visibility section
- [ ] Ran `python tools/lwplugins.py --lpi <project.lpi>`
- [ ] `lazbuild -B` rebuild passes
- [ ] `--form=<registered name>` opens it; `tests/t_plugin.py` passes
- [ ] If the plugin form has a template: `<runtime root>\tpl\<form name>.html` exists with `lw-tpl-mode:window|flat` in the file header, no leftover `.flat.html` in the directory; the template is background only, and control positions are determined by the `.lfm`
